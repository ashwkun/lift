# Lift: ranked production roadmap

Effort key: **S** under a day, **M** a few days, **L** a week or more. Every item below is one merged finding; where two audits found the same gap I kept the stronger evidence and noted the correction.

---

## TIER 0: BLOCKERS

### 0.1 A CI workflow: nothing validates code before a tag ships to every phone (S)

`.github/workflows/` holds android.yml and update.yml, both triggered only by `workflow_dispatch` and `push: tags: ['v*']`; android.yml:35 even has the `branches: [main]` trigger commented out. A tag fires both simultaneously, and update.yml goes from `pnpm install` straight to `eas update` at :142 with no compiler between them, so an OTA can ship JavaScript that does not typecheck to 100% of installs on next launch. The aggregates are also thinner than they read: `pnpm -r lint` prints `Scope: 4 of 5 workspace projects` and reaches only apps/mobile and apps/landing (apps/api and packages/shared define no `lint`), `pnpm -r test` reaches only packages/shared, `pnpm -r build` skips apps/mobile entirely, and apps/mobile has no `test` script at all, which is why items 1.6 and 1.9 have nowhere to put a test today.

**First step:** create `.github/workflows/ci.yml` on `pull_request` and `push: branches: [main]`: `pnpm install --frozen-lockfile`, `pnpm --filter @lift/shared build` (mobile and api typecheck resolve `@lift/shared` through the `default` condition to `./dist`, so this is load-bearing and must come first), `pnpm -r typecheck`, `pnpm -r lint`, `pnpm --filter @lift/shared test`, then a docker job building both Dockerfiles. Add `"lint": "eslint src"` plus a flat config to apps/api and packages/shared in the same commit; the root `eslint.config.js` is expo-only and pnpm filters do not inherit it. Then add `pnpm --filter @lift/mobile typecheck` inside update.yml's existing `Check configuration` block.

### 0.2 A rollback path for OTA, and a staged rollout instead of 100% (S)

update.yml:142 is a bare `eas update --branch "$branch"`, which reaches every install on next launch. `grep -rni 'rollback|roll-back|rollout' .github/` returns one hit, a prose comment at update.yml:11. There is no rollback job, and the README documents at length why the manual workaround does not work: publishing from a working copy resolves a different fingerprint than CI does (`6b8b6d2c` on a dev machine against `797f5e24` in CI across nine module directories), and `eas update:roll-back-to-embedded` resolves runtime version the same way. expo-updates' built-in anti-bricking already covers an update that crashes on launch, so the gap is the update that renders and is wrong: a broken chart, a bad migration guard, a sync regression, which nothing today can retract. The client half is already built: use-app-update.ts:133-135 handles a rollback directive carrying no `updateId`.

**First step:** add `.github/workflows/rollback.yml`, `workflow_dispatch` only, with `branch` and a `mode` choice defaulting to `embedded`, doing the same clean checkout and resolve-runtime-version dance the other two workflows do, then `eas update:roll-back-to-embedded --branch "$branch" --platform android --non-interactive`. Embedded is the right default here because android.yml:245-249 pins `EXPO_UPDATES_FINGERPRINT_OVERRIDE`, so the bundle inside the APK is a known-good build. While in update.yml, print the published update group id to `$GITHUB_STEP_SUMMARY` beside the runtime version it already prints at :157; nothing records it today, and `eas update:republish` needs it mid-incident.

### 0.3 Drop the four unearned permissions before Play sees them (S)

The shipped manifest declares RECORD_AUDIO (:10), MODIFY_AUDIO_SETTINGS (:7), FOREGROUND_SERVICE_MEDIA_PLAYBACK (:5), SYSTEM_ALERT_WINDOW (:11) and READ/WRITE_EXTERNAL_STORAGE (:9, :13), plus an `AudioControlsService` MediaSessionService at :29-33. The app records nothing: sounds.ts:45 passes `allowsRecording: false` and the only sources are `rest_complete.wav` and `countdown_beep.wav`. Two of these are Play declaration forms and a plausible review rejection, and on the sideload path a Microphone line in App info directly contradicts `apps/landing/components/sections/privacy.tsx`, whose entire argument is a checkable ledger.

**First step:** edit `apps/mobile/app.json`: change the bare `"expo-audio"` at :63 to `["expo-audio", { "recordAudioAndroid": false, "enableBackgroundPlayback": false }]`, delete RECORD_AUDIO and FOREGROUND_SERVICE_MEDIA_PLAYBACK from the `permissions` array at :30-32, and add `"blockedPermissions": ["android.permission.MODIFY_AUDIO_SETTINGS", "android.permission.SYSTEM_ALERT_WINDOW", "android.permission.READ_EXTERNAL_STORAGE", "android.permission.WRITE_EXTERNAL_STORAGE"]`. MODIFY_AUDIO_SETTINGS must go in `blockedPermissions`, not just out of the array: withAudio.js:27 pushes it unconditionally outside every option branch and re-adds it on every prebuild. `enableBackgroundPlayback: false` is what removes the MediaSessionService (withAudio.js:60-71), which is the thing a reviewer looking at `foregroundServiceType=mediaPlayback` will ask about. Then add an `aapt2 dump permissions` diff against a committed `apps/mobile/expected-permissions.txt` beside the existing `Verify embedded fingerprint` step; expected final list is 8: ACTIVITY_RECOGNITION, FOREGROUND_SERVICE, FOREGROUND_SERVICE_HEALTH, INTERNET, POST_NOTIFICATIONS, VIBRATE, plus the two the bell needs if you keep them. This moves the fingerprint, so land it with 0.4 and 0.5.

### 0.4 Android auto-backup is silently excluding the database (M)

AndroidManifest.xml:21 carries `android:allowBackup="true"` pointing `fullBackupContent` and `dataExtractionRules` at expo-secure-store's files, which are `<include domain="sharedpref" path="."/>` plus a SecureStore exclude and nothing in `domain="file"`. Android's rule is that once any `<include>` is present, only the named domains are backed up, and the training log is at `files/SQLite/ironlog.db` (client.ts:53). A user who runs Google's copy-your-apps-and-data on a new phone sees Lift appear and opens it to an empty database, having been told by the OS that their data moved. `writeBackupFile()` (backup/index.ts:107) is called from exactly two places, export.tsx:79 and _layout.tsx:393, both manual, so the honest answer to "what happens to a user whose phone dies today" is: everything is gone unless they signed in or happened to tap Export.

**First step:** two edits. Change `apps/mobile/app.json:61` from the bare `"expo-secure-store"` to `["expo-secure-store", { "configureAndroidBackup": false }]`; expo-secure-store's own manifest mod bails with a warning if it finds foreign rules already set, so a competing plugin registered after it is an ordering race. Then add `apps/mobile/plugins/with-backup-rules.ts` writing app-owned `res/xml/backup_rules.xml` and `res/xml/data_extraction_rules.xml` with `<include domain="file" path="SQLite/"/>` plus the existing sharedpref include and SecureStore exclude (the SecureStore keys are hardware-bound and restore as garbage). `SQLite/` sweeps up `ironlog.db-wal` and `-shm`, which is what you want given client.ts sets WAL. Verify with `adb shell bmgr backupnow com.lift.app` then a wipe-and-restore. The scheduled-export half (a new `apps/mobile/src/features/backup/auto.ts` writing to a SAF tree URI, reminded through `features/notifications/reminder.ts`) is the follow-on and is what makes 0.5 survivable.

### 0.5 Release signing, planned around the uninstall rather than the secret (M)

build.gradle:110 and :115 both point at `signingConfigs.debug`, so the APK is not Play-publishable. The part that is not written down anywhere is that fixing it deletes data: a new key means Android refuses the upgrade with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`, every existing user must uninstall, and uninstall deletes `files/SQLite/ironlog.db`. Given 0.4, that is a total loss event for anyone not signed in. `apps/landing/components/sections/install.tsx:30` currently promises the opposite: "New releases install straight over the old one and your log is untouched."

**First step:** do not write a config plugin. android.yml already appends to gradle.properties (:143-193) and proguard-rules.pro (:212-223) after prebuild, and states its own rationale at :136-140 ("This is a property of the build, not of the app, so the workflow is where it goes"), which exists precisely to avoid moving the fingerprint. Add a workflow step that writes the keystore from `ANDROID_KEYSTORE_BASE64` and appends a `signingConfigs.release` block plus a `buildTypes.release.signingConfig` rewrite to the generated `apps/mobile/android/app/build.gradle`, guarded on the secret being present so local `expo run:android` and secretless forks still fall through to debug. app.json never changes and no OTA install is stranded, which removes one of the two break axes entirely. Sequence the other: 0.4 first, then one final OTA on the current runtime showing a one-time `showAlert` (store/dialog.ts:131) telling users to export, then the new key, then enrol in Play App Signing on first upload, then bump the major version and correct install.tsx:30.

### 0.6 AAB, a monotonic versionCode, and a Play track (M)

app.json's `android` block has no `versionCode`, and `@expo/config-plugins`' Version.js:75 is `config.android?.versionCode ?? 1`, so every prebuild emits `versionCode 1` and you could upload exactly one build ever. eas.json is six lines containing only `cli`, android.yml:249 runs `assembleRelease` (Play has required an AAB for new apps since 2021), and no workflow talks to the Play Developer API. Adding versionCode is fingerprint-safe: fingerprint.config.js:39 sets `sourceSkips: ['ExpoConfigVersions']` and its comment names `android.versionCode` as one of the dropped fields.

**First step:** delete the tracked stray `/app.json` at the repo root first. It contains only `{"android":{"package":"com.pawant67.lift"}}`, a different package id from apps/mobile/app.json's `com.lift.app`, and any expo or eas command run from the repo root reads it. Then set `expo.android.versionCode` in apps/mobile/app.json and derive it monotonically in CI from the semver (`major*10000 + minor*100 + patch`, deterministic across reruns unlike `github.run_number`). Add `.github/workflows/play.yml` on `v*` tags: prebuild, `./gradlew :app:bundleRelease` reusing the same gradle.properties and proguard appends, then `r0adkll/upload-google-play@v1` with `track: internal`, `status: draft`, and a `track`/`userFraction` dispatch input. Duplicate android.yml's fingerprint check (:259-268) with the AAB path `base/assets/fingerprint`, or the AAB ships unverified, which is exactly the failure v0.6.1 hit. Skip the eas.json `build` profile: nothing on this path reads it.

### 0.7 The store paperwork, and a privacy policy that is a URL rather than an anchor (M)

`apps/landing/app/` is layout.tsx, page.tsx, not-found.tsx and assets, so the egress ledger in `components/sections/privacy.tsx:29-55` is a section on the home page, and Play requires a dedicated URL. There is no Data Safety answer set, no Apple App Privacy answers, no health declaration for the ACTIVITY_RECOGNITION and FOREGROUND_SERVICE_HEALTH the rest timer forces, no short/full description, and no What's New copy. The screenshots are also the wrong shape: `screenshots/home.png` is 780x1688, a 2.164:1 ratio that exceeds Play's 2:1 maximum. The correct Data Safety answers here are genuinely unusual (no data collected by the developer unless the user opts into a sync server that may not be the developer's) and nobody should be reconstructing that reasoning under a form's time pressure.

**First step:** create `apps/landing/app/privacy/page.tsx` rendering the existing `EGRESS` const as a standalone document with a last-updated date, and add a `privacy` entry to the `links` object in `apps/landing/lib/site.ts:5-29`. This is more urgent than a Play requirement: better-auth's OAuth consent screens and any future email flow need a hosted policy URL too. Then create `store/` at the repo root with `listing/en-US/{title,short-description,full-description}.txt`, `data-safety.md`, `app-privacy.md` and `health-declaration.md`, and add a `--store` preset to `scripts/screenshots/capture.mjs`: use a 540x960 viewport at the existing `SCALE = 2`, or 1080x1920 at SCALE 1, either of which lands a clean 9:16 (1080x1920 at SCALE 2 emits 2160x3840, exactly at Play's per-side ceiling with no margin). For the 1024x500 feature graphic, recrop `apps/landing/app/opengraph-image.png` rather than compositing mark.tsx from scratch.

## TIER 1: TRUST

### 1.1 Four correctness bugs in apps/api/src/sync/sync.service.ts, all in one file (S)

These are one afternoon in one 250-line file and they are the highest-value work in the repo.

**(a) The per-mutation try/catch does not work.** :107-164 catches a write failure and comments "Reject this one mutation rather than failing the whole batch." On Postgres that is false: `db.transaction()` issues a plain BEGIN (postgres-js/session.cjs:133), and postgres.js routes every query through `handler(q)` at src/index.js:291-296 which records the error into a shared `uncaughtError` and rethrows it at :265-266 after the body resolves. So one malformed payload anywhere in a batch of up to 1000 discards every applied row **and every `sync_receipts` insert**, and returns 500. On the client, engine.ts:159 throws out of `pushPending`, `recordFailedAttempt` at :235 never runs, `attempts` stays 0, MAX_ATTEMPTS quarantine never engages, and the poison mutation is re-pushed forever behind a permanently stuck queue showing "The server returned an error (500)". The `invalid` branch at :157-163 is dead code in production.

**(b) `updatedAt` is unbounded client input.** packages/shared/src/sync.ts:57 is `z.number().int()` and :94 feeds it straight to `shouldOverwrite`. A phone with a wrong clock writes a row far in the future; from then on every honest edit loses and comes back `reason: 'stale'`, and engine.ts:189-207 responds by overwriting the local row **and deleting the oplog entry**, so the user's edit is destroyed with no error and nothing left to retry. `serverTime` is already returned by push, pull and status and no client code reads it, so the skew is measurable today and unused. Note mutations.ts:18-20 `touch()` stamps `Date.now()` on every local write, so one skewed clock poisons every row that device authors.

**(c) The `hasMore` boundary truncates a page.** :190-195 limits each of ten tables to `safeLimit`, :208 slices, :209 sets `hasMore = collected.length > safeLimit`. When one table hits its cap with rows behind it and the others return zero, `collected.length === safeLimit` and `hasMore` is false while rows sit past the cursor. engine.ts:360 breaks out believing it is caught up, and the remainder arrives 30 seconds later at the earliest (use-sync-triggers.ts:9). Between runs the local DB holds workouts with partially present sets, which is what analytics, volume totals and PR detection read from. Bulk imports write table-by-table, so long contiguous single-table seq runs are the normal case, not a corner one.

**(d) Ownership and LWW are a read-then-write race.** The tenancy check at :83 and the timestamp check at :94 both read a snapshot `SELECT` with no `FOR UPDATE`, and the write at :139-142 is an unconditional `onConflictDoUpdate` with no `setWhere`. Under READ COMMITTED the commit order decides the winner, not `updatedAt`, which is the non-determinism packages/shared/src/sync.ts:17-21 says the design rules out. The delete at :110-117 has no `user_id` in its WHERE at all.

**First step:** open `apps/api/src/sync/sync.service.ts` and do (c) first, one line: track `if (rows.length === safeLimit) sawFullPage = true` in the per-table loop and use `hasMore = collected.length > safeLimit || sawFullPage`. Then (b): compute `const now = Date.now()` once in `push()` and clamp with `Math.min(mutation.updatedAt, now + SKEW_TOLERANCE_MS)`, using the clamped value for both the comparison and the stored column, returning it on the conflict. Then (d): add `setWhere: and(eq(table.userId, userId), lt(table.updatedAt, effective))` and `.returning({ id: table.id })` so a zero-row result is a lost race reported as a conflict rather than assumed applied, and put `eq(table.userId, userId)` in the delete's WHERE (the writer at :130-137 is hand-cast to a narrow structural type, so this means widening that cast). Then (a): wrap each mutation in `await tx.transaction(...)` so drizzle emits a real SAVEPOINT, **and prove against a live Postgres that the outer transaction still commits**; postgres.js's `uncaughtError` is shared across the whole `begin` closure and the `25P02` special case at src/index.js:272 suggests it works, but this must be tested, not read. If it does not, the fallback is per-table zod validation of `payload` before any statement runs (sync.ts:55 is `z.record(z.string(), z.unknown())`, so nothing checks that `createdAt`/`name` are present or typed). Independently, in engine.ts catch `SyncHttpError` with status >= 500 around the `apiFetch` at :159 and charge `recordFailedAttempt` before rethrowing, so a server-side poison mutation eventually retires.

### 1.2 Stop silent field loss between client and server: a parity test now, a protocol version next (S, then M)

`sanitize()` at sync.service.ts:242-246 does `if (!(key in columns)) continue;` and the mutation is then reported as **applied**, so engine.ts:166 deletes the oplog entry. A client field pushed to a server that has not run the matching migration is destroyed permanently: marked synced locally, gone from the account, no device ever learns. The comment at apps/api/src/db/schema.ts:135-147 exists because this already happened once with `weight_unit`/`distance_unit`. There is drift today: `exercises.thumbnail_url` and `exercises.video_url` exist on the phone (mobile schema.ts:77-78, added by drizzle/0001) and not on the server. It is latent only because custom exercises hardcode both to null (exercises/repository.ts:141-142). The push envelope (sync.ts:62-66) carries `mutations` and `deviceId` and nothing else: no app version, no schema version, no capability field, and `GET /health` returns `{status, time}`, so neither side can tell whether the other is ahead. With OTA and self-hosted servers that lag app releases, divergence is guaranteed.

**First step:** the cheapest high-value item on this list. Create `apps/api/test/schema-parity.test.ts`: import `getTableColumns` from drizzle-orm, `SYNCABLE_TABLES` from @lift/shared, and both schema modules, then assert for each table that `mobileColumns - {sync_state} === serverColumns - {user_id, seq}` in both directions. No database needed and it runs in under a second; the mobile schema imports only `drizzle-orm` and `drizzle-orm/sqlite-core` so Node imports it directly. Add `apps/api/drizzle/0002_*.sql` with the two missing exercise columns to make it green. Note apps/api has no test runner (see 1.6), so either land that first or run this with `node --test --experimental-strip-types` the way packages/shared does. Then the M half: `SYNC_SCHEMA_VERSION` and `MIN_SUPPORTED_PROTOCOL_VERSION` in packages/shared/src/sync.ts, sent as `X-Lift-Protocol`/`X-Lift-Version` from `apiFetch` (auth-client.ts:124-145 is the single choke point for both push and pull), 426 Upgrade Required from a new `apps/api/src/sync/protocol.guard.ts`, `get isUpgradeRequired()` beside the existing `isAuthError` at auth-client.ts:157, and `{status, time, protocol, minProtocol}` from `/health`. Note main.ts:52-55 exempts `health` from the global `api` prefix, so the unauthenticated probe is `GET /health`, not `/api/health`, and custom headers need no CORS work because enableCors reflects `Access-Control-Request-Headers`. Do **not** flip `sanitize` to a hard reject: "unknown columns are stripped, not fatal" is asserted at sync-e2e.py:170. Have it return the dropped keys, log them with userId and table, and escalate only when the declared schemaVersion exceeds the server's.

### 1.3 Catch runtime crashes: an ErrorBoundary, emergency-launch detection, and a crash sink (M)

`grep -rn 'ErrorBoundary|componentDidCatch|ErrorUtils|setGlobalHandler'` across apps/mobile/src returns nothing, and expo-router's useScreens.js:141-155 wraps a route in `Try` **only** when the module exports `ErrorBoundary`, with no default in ExpoRoot. So the careful `StartupError` at _layout.tsx:386-436 covers a failed migration and nothing covers the far more common case, a render throw after boot, which in a minified release goes to the native fatal handler and closes the app mid-session. Separately, `Updates.isEmergencyLaunch` and `emergencyLaunchReason` are not among the eleven fields use-app-update.ts:73-85 destructures, so an OTA that fails to launch self-heals into silence and update-row.tsx reports up to date.

**First step:** `export { ErrorBoundary } from 'expo-router'` in `apps/mobile/src/app/_layout.tsx`. expo-router ships a usable view at build/views/ErrorBoundary.js and re-exports it from the package root, so that one line ships over OTA today with no fingerprint movement; the StartupError-shaped replacement (message, Try again, `writeBackupFile()` export) follows as `apps/mobile/src/components/error-boundary.tsx`. Same commit: read `isEmergencyLaunch`/`emergencyLaunchReason` in use-app-update.ts and add a `'recovered'` status to the `UpdateStatus` union so update-row.tsx's STATES table can say "the last update would not start". For reporting, do not reach for a third-party SDK: privacy.tsx:22 stakes the pitch on "no analytics SDK, no crash reporter". Add `apps/api/src/diagnostics/` with `POST /api/diagnostics/crash` taking stack, `Updates.updateId`, runtime and app version, plus a settings toggle defaulted off. Note it will be the first unauthenticated POST on the server (crashes happen signed out, accounts are optional), so cap the body, bucket by device id, and say so in the module header. Keep a local ring buffer in `apps/mobile/src/lib/crash-log.ts` as the default so the local-first promise holds.

### 1.4 Bound the server: the auth routes have no body limit at all (M)

main.ts:38 mounts `toNodeHandler(auth)` and `express.json({ limit: '10mb' })` is only added at :49, deliberately, for raw-body reasons. better-auth's `toNodeHandler` (node.mjs:3-10) calls `getRequest({ base, request })` and never passes `bodySizeLimit`, so in adapters/node/request.mjs the only bound is the attacker's own declared Content-Length, and for a chunked request with a content-type `content_length` is NaN, `length` is NaN, and the `size > length` guard at :77 never fires. That is unbounded buffering on an unauthenticated route. Beyond that: no throttler on `/api/sync/*` (sync.module.ts is 10 lines, AuthGuard is the only protection) while `pull` accepts `limit: 5000` across ten tables, so one valid account can read 50,000 rows per call in a loop; no `statement_timeout`, `idle_in_transaction_session_timeout` or `max_lifetime` on a pool of `max: 10` (db/client.ts:19-26); `GET /health` runs `SELECT 1` through **the same pool** as sync (app.module.ts:15-19), so the healthcheck queues behind eleven concurrent pushes and Dockerfile:85-86 kills the container after ~90s of saturation; and `grep -rn 'enableShutdownHooks|SIGTERM'` returns nothing, so every deploy tears down in-flight transactions mid-write. CORS also fails open: main.ts:33 passes `origin: true` with `credentials: true` when TRUSTED_ORIGINS is unset and :74-77 logs a warning and serves anyway, and `required('BETTER_AUTH_SECRET')` accepts any non-empty string while .env.example:5 ships `replace-me` (better-auth only throws on its own default and warns below 32 chars).

**First step:** in `apps/api/src/main.ts`, insert a raw byte-counting middleware **before** the auth mount at :38 that destroys the socket past ~256KB, since the express limit at :49 cannot reach that route. Same file: throw rather than warn when `NODE_ENV === 'production'` and `trustedOrigins` is empty, and set `server.requestTimeout`/`headersTimeout` after `listen()` (Node's 300s/60s defaults apply today). In `apps/api/src/auth/auth.ts`, add a `requiredSecret()` rejecting anything under 32 chars or equal to `replace-me` by name, and move to better-auth's `secrets` array (create-context.mjs:69 reads `BETTER_AUTH_SECRETS`) so a leaked key can be rotated without a mass sign-out. Then `helmet` and `@nestjs/throttler` in apps/api/package.json, with a custom `getTracker` returning `request.userId` (the throttler guard must run after AuthGuard for that field to exist), a `connection: { statement_timeout, idle_in_transaction_session_timeout }` block in db/client.ts, a `/ready` split on a dedicated single-connection pool with Dockerfile's HEALTHCHECK pointed at a static `/health`, and `app.enableShutdownHooks()` with an `OnApplicationShutdown` calling `sql.end({ timeout: 10 })`. On auth rate limiting specifically: sign-in is **already** 3 per 10s (rate-limiter/index.mjs:370-384), so the real gaps are that the store is an in-process Map that resets on redeploy, cannot be shared across replicas and evicts FIFO past 1e5 entries, and that the key is `ip|path` (ip.mjs:226-228) so per-account spraying is unmitigated. Set `rateLimit: { storage: 'database', modelName: 'rateLimit' }` and add a per-email counter via `databaseHooks`.

### 1.5 Sign-in on a shared device inherits the previous account's training log (M)

sync-card.tsx:79-83 signs out and calls `resetSyncState()`, which (engine.ts:478-481) deletes the oplog and the `pull_cursor` row and deliberately leaves every workout on the device, correctly, matching the dialog's promise at :72-76. But nothing records **whose** data that is and nothing checks on the way back in: sign-in.tsx:96-115 calls `void sync()` with no identity comparison, and `grep -n 'owner|user_id' apps/mobile/src/db/schema.ts` returns nothing. Sign in as a second account on a family tablet, a resold phone or a demo device and account A's history is now in B's app, feeding B's volume totals, PR detection and analytics, carrying `syncState: 'synced'` with no oplog entries so it can never be pushed or explained. The desktop web build makes this materially more likely, since a browser profile is shared far more often than a phone.

**First step:** persist `owner_user_id` into `sync_meta` (apps/mobile/src/db/schema.ts:347-351) on the first successful sync after sign-in, and compare it before the first `runSync()`. On mismatch offer three choices: merge (re-queue every local row through `trackUpsertMany`, mutations.ts:58, which exists for exactly this bulk case), start fresh (clear the syncable tables, keeping the catalog db/seed.ts seeds), or cancel. While there, make `resetSyncState` clear `owner_user_id` and `DEVICE_KEY`, so the comment at engine.ts:474-476 ("the cursor and device id belong to the previous account") stops claiming more than the code does.

### 1.6 Test infrastructure for the two untested apps (M)

`apps/mobile/src` is 46,623 lines with no runner, no test script and no test file, and apps/api has none either; the root `pnpm test` reaches only packages/shared (280 assertions, not the 41 README:397 claims). The functions computing every number the app displays are in that gap: `finishWorkout` (workouts/repository.ts:1077) and `recalculateWorkout` (:1290) write `totalVolumeKg`, `totalSets`, `prCount` and the `personal_records` rows behind the home screen, stats tab and leaderboard. `features/backup/index.ts` is the app's only escape hatch and its export/import round trip has never been executed by a test. The assumed blocker is wrong: workouts/repository.ts (1,595 lines), analytics/repository.ts, import/repository.ts, sync/engine.ts and db/mutations.ts import zero `react-native` and zero `expo-*` modules, and db/schema.ts imports only drizzle. Server side the blocker is structural: db/client.ts:8-10 throws at module evaluation when DATABASE_URL is unset and sync.service.ts:20 imports that singleton, so `SyncService` cannot be constructed in a testing module at all.

**First step:** `apps/api/src/db/db.module.ts` exporting a `createDb(connectionString)` factory behind a `DB` injection token, and change `SyncService`'s constructor to inject it. ### 1.7 Make the first pull resumable and batched (M)

engine.ts:344-361 loops every page into one `Map`, applies nothing until the loop ends, inserts row at a time at :370-384, and writes the cursor once at :390. A dropped connection on page 20 of 30 discards all 20 and leaves the cursor untouched, so gym wifi can make a large first sync cost the full download on every attempt and never complete. `apiFetch` (auth-client.ts:124-145) has no AbortController, no timeout, no retry and no Retry-After handling, so a half-open socket hangs the run indefinitely. The row-at-a-time apply is the sharper half: on web every one of those inserts crosses the SQLite WASM worker over postMessage. The whole-pull buffering is deliberate, not an oversight: the 27-line comment at :313-339 explains that `seq` is bumped on update so a parent can sort behind its own children and land a page later, and that per-page application previously raised `FOREIGN KEY constraint failed` mid-first-sync.

**First step:** the independent, cheap half, in `apps/mobile/src/features/sync/auth-client.ts:128`: an AbortController with a ~30s deadline, exponential backoff on 5xx/429 honouring Retry-After, and a hard cap on the pull loop's iteration count so a server returning `hasMore` forever cannot spin it. Then batch the apply into multi-row `values([...])` chunks of ~50, the same size db/mutations.ts:70-75 already uses. For resumability, bracket the pull with `PRAGMA foreign_keys = OFF`/`ON` (client.ts already owns that pragma at :75 and :103), commit the cursor page by page in `SYNCABLE_TABLES` order, then run `PRAGMA foreign_key_check` at the end and re-queue any orphan. ## ALREADY STRONG

**The fingerprint discipline around OTA.** `fingerprint.config.js` with documented `sourceSkips`, a written record of which builds are permanently stranded, `EXPO_UPDATES_FINGERPRINT_OVERRIDE` pinned in android.yml:245-249, both workflows printing the resolved runtime version to the job summary, and the embedded `assets/fingerprint` verified in the APK before publish. The measured `6b8b6d2c` vs `797f5e24` note in README:206-222 is the kind of thing most projects learn once and never write down. Do not touch any of it; several proposals above are shaped specifically to avoid disturbing it.

**Local-first with a real escape hatch.** `features/backup/index.ts` with `BACKUP_FORMAT_VERSION` and an explicit refusal path, reachable from the startup-error screen when the database will not open, and running the same code against OPFS in the browser. Two separate audits called server-side export "missing" and were wrong.

**The sync protocol's shape.** The server never reads a value: `sanitize` filters by column name and copies through, conflict resolution is one timestamp comparison, the cursor is a server-assigned sequence unrelated to content, and the only predicate is `WHERE user_id = ? AND seq > ?`. Receipts make replay idempotent, ties go to the incumbent, deletes are tombstones. The bugs in 1.1 are implementation slips inside a design that is correct.

**Comments as a decision log.** engine.ts:313-339 on why the pull buffers whole rather than per-page, button.tsx:265-281 on the Fabric flattening crash, cross-origin-isolation.conf on `add_header` replacing rather than merging and on why COEP is `credentialless`, app.module.ts on the single health endpoint, (tabs)/index.tsx:155-171 on deleting a first-run poster, measurement/[kind].tsx:227-229 on rejecting an undo bar. Six of the audit findings were partly refuted by comments the code had already written, which is the best possible outcome for a comment.

**`scripts/audit-palette.mjs` and the native-module design.** A 292-line contrast auditor with exit codes and `docs/palette-retune.md` behind it; three local Expo modules that degrade to null through `requireOptionalNativeModule`; widgets that read a pre-rendered description and never open the database, so a tap is an ordinary deep link running the same `startSession` the button runs; a foreground service that holds no clock, handing an absolute deadline to a chronometer SystemUI ticks. That division of labour is unusually well thought through.

**`packages/shared` purity.** 280 passing `node:test` assertions over domain logic with no React and no database, and the discipline held: the app-side modules that matter (workouts/repository.ts, analytics/repository.ts, sync/engine.ts, db/mutations.ts, db/schema.ts) import zero `react-native` and zero `expo-*`, which is the only reason 1.6's harness is a config file rather than a rewrite.

Where a verifier contradicted an auditor, these are the calls I made.

**Dropped outright as already shipped.** Server-side data export (backup/index.ts is 417 lines and works in the browser); bodyweight ratios (stats/leaderboard.tsx:223 already prints "1.42x bodyweight", ranked, with a log-a-bodyweight prompt); per-notification Android channels (rest.ts:44 already has a channel map with a legacy migration); COOP/COEP for the web build (cross-origin-isolation.conf already sets both on both locations); a contrast auditor (scripts/audit-palette.mjs exists, and I reframed the finding to "it audits two of eight palettes and runs nowhere"); the "volume zone is only a colour" claim (it renders as text in two screens and prints into the coach document, so the gap is the multi-week trend); RTL swipe mirroring (react-native-gesture-handler already reads `I18nManager.isRTL`).

**Dropped as arguing against a decision the code already made.** A zero-data Home poster ((tabs)/index.tsx:155-171 records deleting one deliberately); moving import higher (profile.tsx:235-247 is already a top-level row carrying the same argument); replacing the set-row delete confirm with an undo bar (the swipe path at :394 has no confirm at all, so the modal is only the long-press and accessibility affordance, and measurement/[kind].tsx:227 already rejected an undo bar with a reason). I kept the durable half of that finding, Recently deleted, which has no substitute.

**Changed the fix because the proposed one would not work.** Deleting RECORD_AUDIO from app.json alone (expo-audio's plugin re-adds it; needs `recordAudioAndroid: false`), and MODIFY_AUDIO_SETTINGS is pushed unconditionally so it needs `blockedPermissions`. Release signing via a config plugin (a workflow-step append avoids moving the fingerprint entirely, which removes one of the two break axes; the uninstall axis remains). Removing `lift://` from TRUSTED_ORIGINS (it is attached as `expo-origin` to every request the Expo client makes, not just OAuth, so removing it breaks sign-in on every phone; the comment at auth.ts:23-28 that says otherwise is itself wrong). Putting a widget-deep-link test in packages/shared (it would invert the monorepo's dependency direction, and the check is not a naive string-to-path one because of expo-router group and dynamic segments). `node --test --experimental-strip-types` for apps/api (Node's stripper refuses the legacy decorators the Nest code uses). A 1080x1920 store screenshot preset at the existing `SCALE = 2` (emits 2160x3840, exactly at Play's ceiling).

**Corrected overstatements that would have misled the fix.** Sex is device-local and never synced, so two findings' GDPR Article 9 framing was wrong; Postgres holds bodyweight and body-fat time series, email, name and per-session IP/User-Agent. Exercise media URLs are not replicated to Postgres (no such column server-side, and built-ins never enter the oplog). Sign-in is not 100 requests per 10 seconds; better-auth already applies 3 per 10s, so the real gaps are storage durability and the IP-only key. The `hasMore` truncation only fires when exactly one table has rows past the cursor, which is still the normal case after a bulk import. The receipts scan is index-only against the primary key, so it is unbounded growth rather than "the dominant cost of the endpoint". A release render throw kills the process rather than white-screening, which strengthens the ErrorBoundary case. And the README makes no performance claims, so the perf-budget finding lost its framing; I kept only the APK-size half.

**One genuine open question, and it gates 1.1(a).** The savepoint fix assumes `tx.transaction()` inside a caught try/catch lets the outer transaction commit. drizzle's postgres-js driver does emit a real SAVEPOINT (session.cjs:155), and postgres.js's `throw e instanceof PostgresError && e.code === '25P02' && uncaughtError || e` at src/index.js:272 suggests the nested scope swallows it, but `uncaughtError` is shared across the whole `begin` closure and I would not ship on a reading of that code. Prove it against a live Postgres with a `[good, NOT NULL violation, good]` batch asserting `applied == [1,3]` before relying on it. If it does not hold, the fallback is per-table zod validation of `payload` before any statement runs, so no statement can error inside the transaction at all, which is worth having regardless since `payload` is `z.record(z.string(), z.unknown())` today and nothing checks that required columns are present or typed.
